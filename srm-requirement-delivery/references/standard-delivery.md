# 标准需求实施链路

仅在标准业务、标准新增适配器埋点或标准新增 API 挂载点模式下读取。三种模式都修改标准仓，但交付边界不同；只执行当前模式的小节。

## 共同准备

1. 确认可写仓库、当前分支、目标模块和仓库内开发约定；先检查已有工作区变更并保留无关修改。
2. 用需求、目标入口和最多两个同模块相似实现建立证据。优先读本地源码；本地缺失时可用 `search_repo` 定位，但只读结果不能代替可写 checkout。
3. 把验收条件映射到代码位置和验证方式。只有会改变正确实现的未知项才标 `TBD` 并追问。
4. 实现后检查 diff，只保留本次需求和必要测试；不要顺手重构、格式化或修改无关配置。

## A. 标准业务需求

适用于标准产品业务行为的新增或修改，不以增加 Marmot 扩展点为主要目标。

### 调查与设计

1. 定位真实业务入口及调用链：Controller、Service、领域对象、持久化层和外部调用只追到能解释本次行为的深度。
2. 明确变更前后契约：请求、响应、状态转换、权限/租户过滤、事务、副作用、幂等、错误与空值语义。
3. 涉及数据库时确认表、字段、索引、迁移方式和回滚兼容；只读核实真实结构，不直接改生产数据。数据库改造只有需求明确要求时才进入实现范围。
4. 涉及对外 API、消息或外部服务时，确认兼容性、序列化结构、超时/重试和失败策略。不能用同名字段或相似接口推断契约。
5. 确定最小实现面和测试面。公共 DTO、接口或表结构的变更必须是验收条件所需，不能作为顺手优化。

### 实现与验证

1. 按目标仓既有分层、异常处理、事务和迁移约定实现；保留向后兼容，除非需求明确要求破坏性变更。
2. 对新增/变化的正常、空值、权限、重复调用和失败分支补定向测试；需要数据库迁移时验证升级路径及必要的回滚/兼容说明。
3. 执行目标模块的编译、测试或仓库约定检查。完整构建不可行时执行最接近变更面的检查，并列明没有覆盖的运行时、集成或数据场景。
4. 交付：业务入口、变更契约、修改文件、测试结果、兼容性/迁移说明和未验证项。明确本次没有新增 Marmot 产物，除非需求另有脚本交付线。

## B. 标准新增适配器埋点

适用于把一个标准业务边界开放为租户 Adapter 能力。交付物是标准常量和调用点，不是租户脚本。

### 埋点契约

编码前确认并记录：

| 项目 | 必须确认的内容 |
| --- | --- |
| 入口 | 标准 `类#方法`、触发条件、单次/批量调用次数 |
| 时机 | 校验前、写入前、成功写入后；事务内还是事务提交后 |
| 身份 | `taskCode`、`runningService` 约定、租户 ID/租户编码来源 |
| 输入 | 传入对象真实类型、必要字段、长整型 ID 类型、可变/只读语义 |
| 返回 | 标准方法是否消费脚本返回值、是否回写业务对象、返回类型 |
| 缺失脚本 | 无租户脚本时跳过、返回原对象还是报错 |
| 异常 | 脚本业务异常是否阻断主流程、日志和回滚语义 |
| 幂等 | 重试、循环或批量场景是否可能重复触发 |

不能只根据编码里的 `BEFORE`/`AFTER` 推断调用位置，也不能默认所有 Adapter 都吞异常或回写返回对象。

### 实施链路

1. 读取目标方法并定位真实业务边界、事务注解/调用关系、状态或数据更新位置。
2. 读取最多两个同模块同类型埋点，确认常量归属、`AdaptorUtils`/`AdaptorTaskHelper` 或实际调用工具、参数顺序、租户来源、返回消费和异常处理。
3. 全仓核对 `taskCode` 常量名和值，避免重复；常量放入该模块现有同类区域。
4. 在确认的边界增加一次最小调用。循环/批量方法必须明确是逐条触发还是整批触发；不得因方便改变调用次数。
5. 只有契约要求标准侧消费返回值时才回写；保持脚本缺失和异常行为与需求及同模块约定一致。
6. 补充能证明触发时机、输入、返回/异常和调用次数的测试；执行目标模块编译/测试。
7. 检查没有创建新结构 `artifacts/adapter`、旧结构 `srm-adaptor`、平台资源或租户配置。若验收条件包含“租户可新建 Adapter”，在标准代码部署到目标 DEV 后用只读 `adapter_event` 注册表核实 `taskCode` 可被平台识别；本地未部署时把它列为部署后验证项，注册表缺失时明确为平台侧阻塞，不能宣称埋点已可配置。
8. 交付时明确后续 Adapter 脚本需要消费的输入与返回契约，以及事件注册表是已验证、待部署后验证还是缺失。

## C. 标准新增 API 挂载点

适用于让标准 Controller API 支持 Marmot API 前置/后置改写。交付物是标准注解和必要编码常量，不是独立脚本或 `api_rewrite` 绑定。

### API 挂载契约

编码前确认：Controller 全限定类名与方法、组合后的 HTTP 方法/完整路径、请求参数和绑定方式、原始返回对象、精确 `apiCode`、现有安全/事务注解，以及后续前置和后置各自可见的数据。

- 前置脚本只按已核实的平台契约修改请求上下文/参数，不能假设可见响应。
- 后置脚本只按已核实的平台契约读取和改写返回结果，不能假设能重新修改已完成调用的 Controller 入参。
- API 前置/后置脚本按平台独立事务语义设计；不要套用 Adapter 与主调用线程的事务假设。

### 实施链路

1. 定位唯一 Controller 方法，核对类级和方法级路由、请求绑定、返回结构及现有注解顺序。
2. 在标准源码中同时搜索 `ApiCode` 常量名和值和 `@MarmotApiPoint` 用法；优先复用需求指定且真实存在的常量。缺失时只在对应常量区域新增需求给出的精确编码，不按接口名猜值。
3. 确认编码未被另一个标准入口误用；同一编码有复用设计时以明确技术设计为准，不能自行判重命名。
4. 在目标方法增加 `@MarmotApiPoint(apiCode = ...)` 和必要导入，不增加 Service Adapter 调用，不改原路由、参数或返回。
5. 补充或执行能证明目标方法、注解编码和原 API 行为未被改变的测试/编译检查。
6. 检查没有创建新结构 `artifacts/independent`、旧结构 `SCRIPT_LIB`、`api_rewrite` 绑定或其它平台资源。若验收条件包含“平台可挂载”，在标准代码部署到目标 DEV 后用 `platform_api_point_list` 核实 `apiCode`、服务和方法可发现；本地未部署时列为部署后验证项，不能把源码注解存在等同于平台已经可挂载。
7. 交付时列出 `apiCode`、完整路由、请求/响应形态、后续前置/后置脚本的可见边界，以及 API 点发现状态。

## 混合标准交付

混合需求中先完成标准业务或扩展点的契约和验证，再让脚本部分消费该已确认契约。若标准源码尚未落地或无法构建，脚本可以先形成带 `TBD` 的草案，但不得把未验证的字段、返回结构或事务语义写成确定事实。
