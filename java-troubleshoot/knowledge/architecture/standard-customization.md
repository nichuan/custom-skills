# 标准 vs 二开的调查规则

> 行为层（Skill 调用本知识时的判定口径），但仓库/分支等动态事实见 `srm-repository-topology.md`。

## 三种二开方式（排障确定二开时必须依次走完）

| 顺序 | 二开方式 | 怎么查 |
|---|---|---|
| 1（最新，优先） | 适配器 JS 脚本（存库） | 查 `sada_adaptor_task_*`，有 `enabled_flag=1` 即命中 |
| 2 | 配置表（虚拟表） | 物理库找不到目标表时，用 `table_code` 查 `spfm_rel_table_definition` / `spfm_rel_table_record`（或租户分表 `spfm_rel_table_record_srm_{租户}`） |
| 3（较老） | Git 二开仓库 `operation-srm-{租户}/srm-{模块}-{租户}` | `gitlab_search_projects` 探测，有则查 `release` 分支 |
| 4 | 无二开 | 以上都查不到 → 走标准逻辑 |

## 判定口径

- 适配器脚本存在且启用 → **以脚本逻辑为准**，标准库代码只作为对照；报告给出脚本 id、task_code 与解码后的关键逻辑。
- 二开库中存在同名类/方法 → **以二开实现为准**，说明二者差异。
- 仅标准库存在 → 结论基于标准实现，并注明"该租户未做此模块二开"。
- 两边都没搜到 → 不要臆断，明确写"未在标准库与二开库中定位到相关实现"。

## 适配器脚本 vs Git 二开并存

有的租户两种都用，有的只用一种；最新方式（适配器 JS 脚本）必须优先于老 Git 二开库排查。
