# MarmotScript 场景检查

这是按需使用的检查指南，不是目标生产版本的 API 签名表。运行时、字段定义和历史配置需要在目标环境另行核实。只读取当前审查涉及的小节。

## 1. 调用契约与关系

先找“谁把什么传给脚本、如何消费返回值”，再判断代码是否正确。Adapter/Independent/CodeBlock 是产物类型；API 前后置、发布、导入、调度、消费和工作流是调用场景，不能由文件名或 quickType 单独推断。

| 场景 | 应取得的事实 | 重点检查 |
| --- | --- | --- |
| Adapter | 标准事件注册、Header/指定 Line、调用点与原 Input | `input.inData.inputParam` 等路径以真实埋点为准；字段名/类型、返回与异常传播、是否在主业务事务中 |
| API 前置 | apiCode、前置关系、标准请求与真实 Context | 请求体/参数/头的改写字段及类型、空 body 与 GET 分支、校验拒绝；前置没有主业务响应 |
| API 后置 | 后置关系、原返回类型与包装、真实 Context | 响应层级、空集合/分页/错误响应、提交可见性、异常是否影响最终响应 |
| API 发布 | 路由、方法、租户/鉴权、发布资源与脚本 | 请求解析、大整数、响应 body/header/httpStatus 的目标契约；Debug 不证明网关路由或发布生效 |
| 数据导入 | 导入模板、校验与导入脚本关系、逐条/批量模式 | 实际 input.data/info/args 结构、行号映射、错误返回、部分成功与重试策略 |
| 调度 | 数字 tenantId、任务编码、脚本关系、参数、时区 | 非登录上下文、失败信号（返回或抛异常）、分页、日期、幂等与重试；不照搬 HTTP 请求模板 |
| Topic 消费 | topic、消费配置指向的 CodeBlock/脚本及调用链 | 消息结构、租户上下文、ack/重试/死信、重复投递和部分更新 |
| 工作流 | 流程/节点绑定、服务定义、serviceMode、scriptCode、serviceCategory | 服务编码与脚本编码各自匹配、执行租户、参数与返回值的转换；不把两种编码假定相同 |
| 跨脚本/CodeBlock | 直接调用和必要的间接依赖 | 参数、返回、异常和副作用传播；未被平台关系扫描命中不等于不可调用 |

API 前后置及发布的交付契约复用 [Marmot 产物实施链路](../../srm-requirement-delivery/references/marmot-delivery.md) 第 6–8 节；不在本 Skill 再维护一份固定 Context JSON 或事务断言。尤其不能仅因后置时机断言异常不影响响应，也不能靠 catch 吞错掩盖失败。

当前 Script Platform 关系实现的检索字段是：`api_rewrite.scriptCode/beforeScriptCode`、`api_publish.scriptCode`、`data_import.validScriptCode/doImportScriptCode`、`scheduler.scriptCode`、`queue_consumer.codeBlockCode`。这用于选择调查对象，实际字段仍由当前能力、定义和精确记录确认；不要沿用旧文档统一 `value3=scriptCode` 的 SQL。消费端可能经 CodeBlock 间接调用 Independent，需要按实际依赖继续核对。

`platform_relations_get` 当前返回 `scan_scope.complete=false`，仅提供有限扫描证据，不能证明无引用。按租户调用需传真实数字 `scheduler_tenant_id`；缺失时不要靠全局扫描猜调度租户。多入口分别检查，单入口问题无需强制穷举全部场景。

### 工作流专项

若服务确实是 SCRIPT 模式，按服务定义的 `scriptCode` 找脚本，再按流程绑定的 `serviceCode` 找服务。二者可不同；单凭脚本 code 查 service_code 可能漏查。仅在实际流程涉及共享服务时核对 0 租户继承、服务定义租户和脚本执行租户，不默认扩大普通业务数据范围。

按目标版本返回消费逻辑核实：

- 审批候选规则：需要何种员工/用户标识、列表包装与转换、空候选如何处理；不要仅凭“能转字符串/数组”推断审批人一定正确。
- 跳转条件：消费者要求的布尔类型及字符串转换；不要用 JS truthiness 代替目标转换约定。
- 附加动作或其它服务类别：返回值是否被使用、异常是否阻断、调用是否可重复及写入事务。

平台未覆盖的工作流配置通过已确认环境中的 Archery 结构/记录与必要调用源码验证，不伪造平台 resource_type，不凭一个固定实现推广所有版本。

## 2. 运行时 API、类型与精度

### 签名核实

只检查脚本实际引用的 API 和其直接依赖：

1. 对照目标版本的模块 `index.js`/导出包装：参数是否是对象、位置参数、单值或数组，默认值与响应解析在哪一层发生。
2. 有 Java 桥接时核对全部相关 helper 重载、集合转换、返回值和异常处理；简化的 `.d.ts` 或参数个数本身不足以定因。
3. 查清目标模块可用性、版本与匿名上下文；旧 STD/BIZ 封装与新 require 可各自合法，不因风格替换现有实现。

如需核实源码，可经 `search_repo` 定向找 `GraalContextSpecification`、`ScriptStaticEngine`、目标 `@M` 模块与相应 helper；路径来自当前工作区/工具返回，不固定他人的路径或生产 hotfix 分支。

### 静态模块规则

`check_marmot_script_static` 默认拒绝 require 依赖。`rules_json.allowed_runtime_modules` 可放行经目标运行时核实的精确字面量路径，只接受 `@M/v1/<模块>` 或 `@M/2021/std|biz|other`；不支持 Node 模块、相对路径、动态 require 或任意前缀通配。

例如只有已证实目标提供 object/logger2 时才传：

```json
{"allowed_runtime_modules": ["@M/v1/object", "@M/v1/logger2"]}
```

放行只解决“该模块依赖被误认作 Node”的问题，不证明模块存在、方法签名或运行正确。其它合法第三方封装若不在工具支持的路径形态内，保留工具限制并按目标运行时证据解释，不扩大放行规则。检查器仍是词法检查，注释、字符串与别名调用需要人工复核，不能当作完整依赖分析。

### 类型检查

读项目实际 jsconfig/tsconfig 和运行时声明来源，不根据目录中文名判是否受检。TS2307 既可能是声明缺失也可能是模块名拼错；TS2304 既可能是注入全局缺声明也可能是真正未声明变量；TS2339 也可能是简化声明遗漏。结合模块、源码与声明判断。

`unknown` 结果应通过已知对象类型、局部 JSDoc、空值验证和类型收窄访问。不得把整个 object 模块强转 `any` 作为统一修复；确有动态边界且无法声明时，把局部断言与未验证范围写清楚。

### 精度与外部响应

- 整型 ID 跨 JSON/字符串/Java/数据库时验证精度，不用 `Number` 或 JS 默认解析把超出安全整数的 ID 改写。安全 JSON 封装的具体行为也要核对。
- 金额/比率按业务精度与目标十进制能力处理；JSONbig 不等于十进制运算正确，不对所有字段强制同一个解析器。
- HttpClient/Feign/接口 SDK 要检查实际响应包装、HTTP 状态与业务失败字段；HTTP 200 不证明业务成功。
- OutBound/服务限制只查实际目标域名或服务，不直接测试连通性。日志仅保留脱敏业务 key、数量、状态，不输出凭据或完整敏感对象。

## 3. 数据对象、租户与更新

- 先识别实际访问接口和逻辑对象：物理表、对象服务、Rel-Table/虚拟表、QueryBlock 不能互相替代。真实 schema、分表名称与映射应从已确认实例、平台定义或结构取得；不能只把租户编码小写就作为物理表名。
- 业务表按确认的租户谓词过滤；共享配置只在已核实的继承语义内读取 0 租户。Rel-Table 的租户存储方式按当前结构与记录确认，不一律删除 tenant_id 条件。
- 物理库查无对象时核查是否逻辑对象、不同数据源或权限范围。缺表/字段是可验证问题；查询失败、无权限或样本为空是证据缺口。
- QueryBlock/CodeBlock 按编码、租户、版本、内容与调用参数核对；本地对应文件只证明本地产物。绑定未查到或当前扫描不完整时不自动判未部署。
- 拦截器对 SELECT 与 DML 的 schema、租户、权限、事务行为可能不同。跨库 SELECT 成功不证明写入同样可路由；不能建议手拼 schema 或直接物理表绕过受控 API/黑名单。
- 写入按目标 update/updateOptional 的版本、指纹、可选字段和空值语义审查：记录来源、版本是否正确、写范围是否匹配。保留平台并发保护，不用 updateOptional 绕过冲突；也不无条件给出“业务层永不做版本校验”的规则。

## 4. 调度、分页、失败与事务

调度的输入、失败信号、匿名上下文、返回值是否被使用及事务边界都由目标执行器确认。若目标执行器丢弃返回值，则 `return false` 不能标记任务失败，需要其支持的异常/失败机制；抛异常也不证明外部系统副作用回滚。

重点审查：

- 分页起点以实际 API 为准；更新会让记录退出查询条件时，`page++`/offset 会跳过剩余记录。选择稳定 keyset/水位、反复首批、或有合理内存边界的先取 ID 后分批更新，并检查终止条件与重复处理。
- 先全量收集也有内存、并发变更与事务时间风险，不作为唯一正确方案；批量限制与 CPU/内存/超时取目标配置，不固定“100/10000/340s”。
- 日期以业务时区及目标日期工具处理，UTC ISO 截日可能偏一天；不要把所有租户写死 UTC+8，也不要引用目标未安装的 moment-timezone。
- 匿名、调度或消费上下文不当然拥有登录用户；executionTenantId 的来源、执行租户与业务数据租户分别核实。
- 重复调用、消费重试与任务重跑分别检查幂等 key、唯一约束、进度、部分成功。异常吞掉后返回成功可能阻止重试或保留部分更新，应核对真实失败策略。
- Adapter、API 前后置、工作流、调度与外部服务的事务边界不互相照搬。代码中的 throw、日志 ERROR 或 FakeTxInfo 不能单独证明主业务回滚；需要实际传播、提交与持久化证据。
- 外部 HTTP 500/SOAP Fault 只证明远端响应异常；请求内容或本地映射变化也可能触发，不能据此单独归责远端。

## 5. 审查记录

普通审查可用一张表交付，重点是可核对证据，不强制建报告文件：

| 项目 | 记录 |
| --- | --- |
| 对象 | 来源、完整/片段/diff、租户/环境、类型、精确身份、版本/哈希 |
| 适用调用场景 | 入口与关系证据、真实 Input/返回消费者、未覆盖范围 |
| 问题 | 位置、条件、影响、证据、置信度、最小建议 |
| 检查 | 语法、词法静态规则与 hash、人工 API/契约、类型、运行验证分别记录 |
| 缺口 | 尚缺的最少证据，是否会改变结论 |

生产根因报告仍由 java-troubleshoot 汇总；沿用已取日志，不为“补齐审查”再次拉同一 trace。比较同租户同接口最后成功与首次失败，核对其间源码、配置、部署与脱敏请求变化；相关变更是线索，必须与实际失败路径连接后才能定因。
